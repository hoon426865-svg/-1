# 온워크 · 직원 출퇴근 및 생산량 관리

Node.js 24 이상이 필요합니다. 로그인한 직원은 본인 출퇴근·생산 기록만 조회·입력하며, 관리자는 직원 계정·작업 종류와 전체 집계를 관리합니다. 데이터는 SQLite에 저장됩니다. 체험 직원 선택과 자동 예시 데이터는 로그인 화면에서 사용하지 않습니다.

## 설치와 최초 관리자 설정

```bash
node --version
npm ci
export DATABASE_PATH="$PWD/data/onwork.sqlite"
export SITE_ID=local-site
unset APP_ORIGIN  # Codespaces에서는 전달 포트 HTTPS 주소를 자동으로 선택합니다.
```

앱을 실행한 뒤 브라우저에서 최초 관리자 계정을 설정합니다.

```bash
npm start
```

1. Codespaces의 **포트(Ports) → 3000 → 브라우저에서 열기**로 접속합니다.
2. 관리자가 아직 없으면 **최초 관리자 설정** 화면이 자동으로 표시됩니다. 관리자 계정(영문·숫자·하이픈 1~30자), 비밀번호(12~128자), 비밀번호 확인을 입력하세요.
3. **관리자 계정 만들기**를 누르고, 완료 후 방금 만든 계정으로 로그인합니다. 비밀번호는 코드·로그·브라우저 저장소에 보관하지 않으며 DB에는 솔트가 포함된 해시만 저장합니다.
4. 관리자가 있거나 최초 설정을 완료한 DB에서는 `/setup` 재진입을 로그인 화면으로 보내고, 초기 설정 API의 추가 생성 요청은 서버에서 409로 거부합니다. 동시 제출과 서버 재시작 후에도 다시 생성할 수 없습니다. 기존 데이터는 초기화하지 않습니다.

터미널에서 초기 설정을 하는 기존 방법도 유지합니다. 필요한 경우 `bash scripts/setup-admin.sh`를 직접 실행하면 숨김 입력으로 계정을 만들 수 있습니다. 웹·터미널 설정은 같은 일회성 잠금을 사용하므로 어느 쪽이든 먼저 완료하면 다른 쪽은 차단됩니다. 비밀번호를 채팅·소스·README에 넣지 마세요.

앱 시작에는 `DATABASE_PATH`가 반드시 필요합니다. `.env`를 자동으로 읽지 않으므로 환경 변수를 셸 또는 실행 환경에서 설정하세요.

브라우저에서 `APP_ORIGIN` 주소를 열어 관리자 계정으로 로그인하세요. Codespaces에서는 3000 포트를 전달하고 **포트(Ports) → 브라우저에서 열기**로 접속하세요. `APP_ORIGIN`을 지정하지 않으면 `CODESPACE_NAME`, `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN`, `PORT`에서 정확한 HTTPS 주소를 자동으로 계산합니다. 일반 로컬 실행은 `http://localhost:3000`을 기본값으로 사용합니다. 직접 주소를 지정하려면 **브라우저에 표시되는 정확한 HTTP(S) 주소(끝 슬래시·경로 제외)**를 `APP_ORIGIN`으로 설정하세요. 명시한 값이 자동 설정보다 우선합니다. 다른 포트를 쓰면 `PORT`와 `APP_ORIGIN`을 함께 변경합니다. 기본 수신 주소는 `0.0.0.0`이며 `HOST`로 변경할 수 있습니다. HTTPS 주소에서는 Secure 쿠키를 사용합니다. 운영 환경에서는 `NODE_ENV=production`, HTTPS `APP_ORIGIN`, `SITE_ID`를 지정하세요.

## 직원 계정과 사용 방법

1. 최초 설정 후에는 로그인한 관리자만 **직원 관리**에서 이름·사번·소속 팀·임시 비밀번호·변경 사유를 입력하여 직원을 추가합니다. 시험용 계정은 가상의 이름과 별도로 만든 임시 비밀번호를 사용하세요. 공용 기본 비밀번호는 제공하지 않습니다.
2. 직원은 본인의 사번과 임시 비밀번호로 로그인합니다. 최초 로그인에서는 비밀번호 변경만 가능하며, 변경 후 새 비밀번호로 다시 로그인합니다.
3. 직원 화면에서 **출근하기·퇴근하기**, 작업별 **수량 기록하기**를 사용합니다. 본인 기록만 보이며 기록 시각은 서버의 한국 시간을 기준으로 합니다. 출퇴근 버튼은 이번 단계에서 계정 인증으로 기록하며 QR 검증을 요구하지 않습니다.
4. 관리자는 날짜별 전체 출퇴근·생산 합계를 확인하고 직원 정보 수정·퇴사 처리·재활성화 및 작업 종류 관리를 이용합니다. 퇴사 처리 즉시 해당 직원 세션을 무효화하고 기존 기록은 보존합니다.
5. 직원의 비밀번호를 잊은 경우 관리자가 **직원 관리 → 비밀번호 재설정**에서 새 임시 비밀번호·확인·변경 사유를 입력합니다. 즉시 기존 직원 세션을 종료하고, 직원은 임시 비밀번호로 로그인한 뒤 새 비밀번호로 변경해야 합니다.
6. **새로고침**으로 다른 기기에서 변경한 기록을 가져오고, 사용 후 **로그아웃**합니다. 자동 실시간 갱신은 아직 없습니다.

로그인하지 않은 업무 화면 요청은 로그인 화면으로 이동하고 API는 401을 반환합니다. 관리자 주소와 `/api/admin` 전체 경로는 서버가 계정을 검사하여 미로그인은 401, 직원은 403으로 거부합니다. 직원 요청의 `employeeId` 또는 `employee_id`가 본인과 다르면 조회·입력 모두 403이며, 실제 저장 대상은 세션에서 결정합니다. 세션은 HttpOnly·SameSite 쿠키로 관리하고 변경 요청에는 Origin 및 CSRF 검사를 적용합니다. 임시 비밀번호를 변경하기 전에는 업무 API를 사용할 수 없습니다.

## 이번 단계의 범위와 남은 기능

화면에서의 일회성 최초 관리자 생성, 로그인·로그아웃·최초 비밀번호 변경, 직원 본인 기록 조회·입력, 관리자 직원 관리·전체 집계를 화면과 서버에 연결했습니다. DB 저장 내용은 재시작 후에도 유지됩니다.

QR·백업 기능은 기존 서버 코드와 스크립트를 유지하며 이번 단계에서 확장하지 않았습니다. QR 표시·카메라 스캔, 관리자 기록 정정·야근 승인·감사 이력·영구 삭제용 화면은 아직 연결하지 않았습니다. 기존 체험판의 메모리 완전 삭제 버튼은 운영 DB를 삭제하는 버튼으로 전환하지 않았습니다. 야근 검토 표시는 승인이나 수당 확정이 아닙니다.

`lib/backup.mjs`, `scripts/backup.mjs`, `scripts/restore.mjs`는 기존 DB 백업·복구 코드입니다. 자동 검증은 임시 DB에서 수행하며 실제 앱의 최초 관리자 정보는 사용자가 화면에서 직접 입력합니다.

## 검사

```bash
npm test
```

테스트는 메모리 DB 또는 임시 디렉터리를 사용합니다. 관리자 API와 주소 접근 거부, 타인 ID 조회·입력 거부 및 데이터 미변경, 본인 출퇴근·생산 기록, 관리자 직원 관리·전체 조회, 임시 비밀번호 변경, 로그아웃·퇴사 시 세션 무효화, 기존 QR·백업·DB·도메인 동작을 검사합니다. HTTP 통합 테스트는 실제 서버를 임시 포트에서 실행합니다.

### 검증 결과와 브라우저 확인 대기 항목

Node.js 24.21.0에서 기존 Node 테스트 도구로 API·DB·실제 HTTP 서버와 `server.mjs` 실행 및 재시작을 검사했습니다. HTTP 테스트에서 확인하는 HTML 응답 성공은 브라우저 렌더링이나 폼 조작 성공을 뜻하지 않습니다. 브라우저에서 로그인부터 화면 조작까지의 확인은 아직 수행하지 않았습니다. Playwright 설치는 더 시도하지 않습니다.

샌드박스에서 `tests/http.test.mjs`가 실패한 원인은 `listen EPERM: operation not permitted 127.0.0.1`이었습니다. 로컬 포트 실행이 허용된 환경에서 같은 테스트를 실행해 통과했습니다. 테스트를 건너뛰거나 실패를 성공으로 처리하지 않습니다. 개별 검사와 자세한 오류 출력은 다음 명령으로 확인할 수 있습니다.

```bash
node --test --test-isolation=none --test-reporter=spec tests/http.test.mjs
node --test --test-isolation=none --test-reporter=spec tests/*.test.mjs
```

브라우저에서는 위 초기 설정을 마친 후 아래 순서로 직접 확인해 주세요. 아래 항목은 **수동 검증 대기**입니다.

1. 빈 DB에서는 최초 관리자 설정 화면에서 계정을 만들고, 이후 `/setup` 재진입과 재생성이 차단되는지 확인합니다. 설정 완료 후 로그아웃 상태에서 `/employee`, `/attendance`, `/production`을 열면 로그인 화면으로 이동하는지 확인합니다. `/admin` 직접 접근은 401 응답이어야 합니다.
2. 관리자로 로그인하여 관리자 화면과 전체 집계를 확인하고, 서로 다른 시험용 직원 두 명을 등록합니다. 직원 비밀번호 재설정 후 기존 세션 종료와 임시 비밀번호 변경 흐름도 확인합니다. 실제 직원 자료를 사용할 필요는 없습니다.
3. 별도 브라우저 프로필이나 시크릿 창에서 각 직원으로 로그인합니다. 임시 비밀번호 변경 후 재로그인이 되는지, 관리자 메뉴와 체험 직원 선택이 없는지 확인합니다.
4. 각 직원이 출퇴근·생산량을 입력하고 새로고침합니다. 본인 기록만 보이는지, 관리자는 두 직원의 합계를 볼 수 있는지 확인합니다.
5. 직원 로그인 창에서 `/admin`과 `/api/admin/audit`를 직접 열면 403이어야 합니다. 개발자 도구 콘솔의 `fetch('/api/state?employeeId=OTHER-ID').then(r => r.status)`도 403이어야 합니다. `OTHER-ID`는 본인과 다른 ID입니다. 실제 직원 ID나 비밀번호를 공유할 필요는 없습니다.
6. 로그아웃한 뒤 업무 주소를 다시 열면 로그인 화면으로 이동하고, 로그아웃 전 세션으로 업무 API를 호출하면 401인지 확인합니다. 관리자 화면에서 시험용 직원을 퇴사 처리한 뒤 해당 직원의 다음 요청도 차단되는지 확인합니다.
7. Codespaces의 실제 HTTPS 주소에서 로그인·새로고침·로그아웃을 확인합니다. 로컬 HTTP 테스트만으로는 전달 포트의 HTTPS·쿠키 동작을 검증할 수 없습니다.

## Git에 포함하지 않는 자료

`.gitignore`는 `node_modules`, `.env` 계열, 키·인증 파일, `data/`, `private/`, `exports/`, 직원 자료·스프레드시트, DB·저널·덤프·백업 파일을 제외합니다. 실제 직원 자료는 제외 경로에 보관하세요. `.gitignore`는 소스에 직접 입력한 개인정보나 비밀번호까지 감지하지 못하므로 커밋 내용을 확인해야 합니다. 운영 비밀번호와 인증키를 테스트 코드에 넣지 마세요.

## 실행 오류

- `DATABASE_PATH 환경변수가 필요합니다`: 위 환경 설정을 같은 터미널에서 실행하세요.
- `EADDRINUSE`: 사용 중이지 않은 `PORT`를 지정하고 `APP_ORIGIN`도 맞추세요.
- `EPERM` / `EACCES`: 서버 포트 또는 DB 경로 접근 권한을 확인하세요.
- 로그인 요청이 403이면 브라우저 주소와 `APP_ORIGIN`의 프로토콜·호스트·포트를 확인하세요.

### Codespaces의 요청 출처 오류

`허용되지 않은 요청 출처입니다`는 서버가 받은 Origin이 설정된 앱 주소와 다르거나 누락됐다는 뜻입니다. 브라우저가 올바른 주소를 보내도 Codespaces 프록시가 localhost로 변경할 수 있으며, 이 경우 아래의 프록시 대응 검사가 필요합니다. 관리자 계정이 없는 문제와 별개입니다. README의 과거 `APP_ORIGIN=http://localhost:3000` 설정을 HTTPS 미리보기에서 사용하면 발생할 수 있습니다.

1. 서버를 실행한 터미널에서 Ctrl+C로 종료합니다.
2. 같은 터미널에서 아래 명령으로 오래된 수동 주소를 해제하고 실행합니다. 기존 DB는 유지됩니다.

```bash
export DATABASE_PATH="$PWD/data/onwork.sqlite"
export SITE_ID=local-site
export PORT=3000
unset APP_ORIGIN
npm start
```

3. 시작 로그의 HTTPS 주소와 Ports 탭의 주소가 같은지 확인하고, 별도 브라우저 탭에서 그 주소의 `/login`을 여세요. 내장 미리보기가 다른 출처를 보내면 별도 탭을 사용하세요. 운영 모드에서는 자동값 대신 HTTPS `APP_ORIGIN`을 명시해야 합니다.

출처 검사를 끄거나 모든 `*.app.github.dev` 주소를 허용하지 않습니다. `Host`·`X-Forwarded-Host` 헤더로 신뢰할 주소를 결정하지 않으며, 누락·`null`·다른 Codespace 출처도 거부합니다. 비밀번호를 다시 입력해도 출처 설정 불일치는 해결되지 않습니다.

실제 Codespaces HTTPS 전달 경로에서 HTTPS Origin이 서버에 도착할 때 `http://localhost:3000`으로 변경됨을 확인했습니다. 이 변환을 고려하지 않은 기존의 단일 Origin 비교가 요청을 거부하는 원인이었습니다. 수정 후 같은 실제 전달 경로의 출처 검사가 HTTP 200으로 통과했습니다. 화면에서 서버의 앱 주소와 현재 주소가 다르면 비밀번호 입력 전에 올바른 주소 링크를 표시합니다. 브라우저의 실제 렌더링·폼 조작 및 전달 포트 쿠키 동작은 수동 검증 대기입니다.

### Codespaces 프록시의 Origin 변환 대응

Microsoft 터널은 포트 전달 과정에서 Origin을 `http(s)://localhost:포트`로 바꿀 수 있습니다([Microsoft 구현](https://raw.githubusercontent.com/microsoft/dev-tunnels/main/ts/src/contracts/tunnelOptions.ts)). 외부 HTTPS Origin을 그대로 넣은 로컬 HTTP 테스트만으로는 이 경로를 검사할 수 없습니다.

앱은 직접 전달된 정확한 `APP_ORIGIN`을 계속 허용합니다. 변환된 localhost Origin은 다음 조건을 **모두** 만족해야만 허용합니다: 현재 Codespace·포트에서 계산한 HTTPS 주소가 APP_ORIGIN과 일치하고, localhost 포트가 정확하며, Referer의 출처와 화면이 보낸 X-Onwork-Origin이 그 HTTPS 주소와 일치하고, 브라우저 Sec-Fetch-Site가 same-origin이어야 합니다. 일반 환경·다른 Codespace·다른 포트·누락된 증거는 거부합니다. 세션 CSRF 검사도 유지합니다.

Referrer-Policy는 same-origin으로 설정하여 같은 앱 안에서만 Referer를 전달합니다. 외부 사이트에는 전달하지 않습니다. 로그인·최초 설정 폼을 표시하기 전에 비밀번호 없는 `/api/origin-check` 요청으로 실제 프록시 경로를 검사합니다. 실패 시 받은 Origin과 Referer의 출처만 표시하고 경로·쿼리·비밀번호·쿠키는 출력하지 않습니다. 이전 탭은 새로고침해야 새 클라이언트 코드가 적용됩니다.

## 근무 변경 신청과 처리

직원 로그인 후 기존 출퇴근·생산 기록 아래 **내 근무 변경 신청**에서 야근·추가 근무, 연차, 월차, 조퇴, 결근·기타 부재를 신청합니다. 시작일·종료일, 매일 적용할 시간 또는 종일 부재, 사유를 입력합니다. 추가 근무와 조퇴는 시간을 지정해야 합니다. 날짜 범위는 양 끝 날짜를 포함하며 최대 366일입니다. 주말·공휴일도 포함되므로 제외할 날짜는 나누어 신청합니다. 자정을 넘는 시간은 날짜별로 나누며 하루 종료 시각에 `24:00`을 사용할 수 있습니다.

- 직원은 본인의 신청과 전체 변경·처리 이력만 조회합니다. 대기·반려 신청은 변경 사유를 남기고 수정·재신청할 수 있습니다.
- 관리자는 **근무 변경 신청 관리**에서 신청 대상 날짜·직원·유형·현재 상태로 조회하고 의견을 입력해 승인·반려합니다. 처리자 계정과 처리 시각(화면은 한국 시간)을 기록합니다.
- 승인·반려 후 정정은 관리자가 사유를 남겨 **재검토로 되돌리기**를 선택합니다. 이후 직원이 수정하고 관리자가 다시 처리합니다. 재검토 중에는 승인 집계에서 제외됩니다. 종전 신청 내용과 모든 승인·반려 이력은 보존됩니다.
- 동일 직원의 대기·승인 신청이 날짜와 시간 모두 겹치면 유형에 관계없이 거부합니다. 시간대가 인접하거나 서로 겹치지 않으면 신청할 수 있습니다. 반려 건은 중복 범위에서 제외합니다. 중복 승인과 오래된 화면에서의 수정은 409로 거부하므로 새로고침 후 확인합니다.
- **직원별 월간·연간 내역**에서 연도·월(연간 전체 가능)·직원을 선택하면 최신 상태별 신청 수, 승인된 추가 근무 시간, 승인된 부재가 있는 날짜 수와 출퇴근·생산량을 함께 봅니다. 상세 내역에서 처리 이력을 열 수 있습니다. 집계는 신청 대상 날짜 기준이며 기간을 넘는 신청 시간은 조회 기간에 해당하는 날짜만 합산합니다.
- 부재 일수는 부분 부재를 포함한 **중복 없는 날짜 수**입니다. 같은 날짜에 부분 부재 두 건이 있어도 1일로 표시합니다. 휴가 차감 일수나 근무일 수가 아니며, 연차·월차 부여·잔여량·차감 규칙은 구현하지 않습니다. 승인된 추가 근무 시간은 실제 출퇴근에 의한 근무 시간이나 수당 확정 값이 아닙니다.

DB 시작 시 `work_requests`, `work_request_history` 테이블과 보존용 트리거·인덱스만 추가합니다. 기존 테이블과 계정·출퇴근·생산 기록은 초기화하지 않습니다. 신청 이력이 있는 직원은 영구 삭제를 차단하며 퇴사 처리로 보존합니다. 신청 삭제 API는 제공하지 않으며 이력은 UPDATE/DELETE를 DB 트리거에서도 차단합니다.

검증: `node --test --test-isolation=none --test-reporter=spec tests/*.test.mjs`. 모든 자동 테스트는 메모리 또는 임시 DB에서 실행합니다. 실제 계정으로 시험 데이터를 자동 생성하지 않습니다.

화면 확인 순서:

1. 직원으로 로그인하고 **내 근무 변경 신청**에서 신청합니다. 신청 목록의 대기 상태와 **변경·처리 이력**을 확인합니다.
2. 관리자 로그인 후 **근무 변경 신청 관리**에서 해당 직원을 조회하고 관리자 의견을 입력해 승인 또는 반려합니다.
3. 직원 화면의 **새로고침**을 눌러 결과·처리자·처리 시각·의견과 이력을 확인합니다.
4. 관리자 **직원별 월간·연간 내역**에서 해당 월 또는 연간 전체를 조회하고 직원 상세의 신청·출퇴근·생산량을 확인합니다.
5. 정정은 관리자 재검토 → 직원 수정·재신청 → 관리자 재처리 순서로 확인합니다. 이전 처리 이력은 계속 남습니다. 실제 DB에서 입력한 신청은 보존되므로 실제 필요한 신청으로 확인하거나 별도 시험 DB를 사용하세요.
