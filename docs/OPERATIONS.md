# 품질·생산·자재 관리 확장

직원별 수량만 기록하던 온워크에 품목·도면번호·LOT 생산, 담당자 검토, 자재 입출고 및 품질검사를 추가한다. 기존 계정, 패스키, 출퇴근, 작업, 생산, 신청 기록은 그대로 유지한다.

## 업무 흐름

- 관리자는 설정에서 품목, 모델, 공급업체, 검사기준, 출처, 확인 사항과 업무별 담당자를 관리한다. 일반 직원은 본인 생산만 입력·조회하며, 생산 검토/자재/품질 권한은 각각 서버에서 검사한다. 생산 담당자는 본인 기록을 승인할 수 없다.
- 직원의 품목·LOT 생산 기록은 기존 `production`에도 한 번만 저장되어 기존 합계와 보고서에 포함된다. 대기·반려 기록은 본인이 정정·재신청할 수 있다. 승인된 기록은 잠근다. 기존 작업별 수량 입력과 중복 입력하지 않는다.
- 생산 승인 시 양품은 검사 대기 LOT 재고가 된다. 동일 품목·LOT의 중복 입고는 차단한다. 공정별 생산 단위와 LOT를 구분해야 한다. 부품 소요량이 확정되지 않아 BOM 자동 차감은 하지 않는다.
- 자재 담당자는 입고, 출고, 증감 조정, 폐기를 기록한다. 검사 대기/부적합 보류 LOT의 출고, 음수 재고, 수량 초과를 차단한다. 재고 증가 조정은 재검사를 위해 대기로 돌린다.
- 품질 담당자는 수입/공정/출하검사, 시료 수량, 불합격 수량, 적용 기준, 실측 결과, 사유를 기록한다. 합격은 사용 가능, 불합격은 LOT 전체 보류다. 재검사는 새 검사 기록이다. 검사 당시 품목 기준과 출처를 보존한다. 수치 공차 자동 판정은 하지 않으며 검사자가 기준 적용 여부를 확인한다.
- 모든 변경은 감사 이력과 재시도 식별자를 보존한다. 원장/검사 결과는 수정·삭제하지 않는다. 잘못된 재고는 사유 있는 조정, 잘못된 판정은 재검사로 이력을 추가한다.

## 보존 및 검증

`0008_operations.sql`은 테이블/인덱스/보호 트리거만 추가한다. 기존 행을 갱신하거나 초기화하지 않는다. Node와 Worker는 같은 업무 로직을 사용한다. D1의 기존 revision/guard 원자적 배치로 승인·입고·원장·감사·중복 방지를 함께 커밋한다. 연계 생산은 기존 수정/테스트 삭제 경로로 우회할 수 없다. 업무 이력이 있는 직원은 퇴사 처리로 보존한다. 백업/SQLite→D1 이전에 새 테이블을 포함한다.

2026-11-09 검증:

- 전체 Node 회귀 검사와 Worker 회귀 검사 실행. 업무 시나리오에서 역할 분리, 본인 생산, 타인 검토, 반려 후 정정, 대기/부적합 출고 거부, 재검사, 초과 출고 거부, 원장 잔량, 재시도, 권한 해제를 확인.
- D1 쓰기 중 인위적 오류를 주입해 LOT/원장/감사/요청 식별자가 함께 롤백되고 같은 요청 재시도가 성공하는지 확인.
- 운영 확장 마이그레이션 전후 기존 계정/직원/생산/감사/세션 내용 동일성 확인.
- 분리된 합성 데이터 브라우저에서 관리자 9개/일반 직원 5개 메뉴, 생산 입력→승인, 입고→검사 합격, 설정 기준 편집 및 앱 새로고침 시 초안 보존 확인.
- 원본 자료에서 만든 비공개 품목 JSON 64개를 동일 관리자 API로 검증. 회사 원본/공급자/검사기준 JSON은 공개 Git에 포함하지 않는다.

목록은 50건씩 이전/다음 페이지로 조회한다. 이력 화면은 최근 50건을 보여주며 전체 이력은 DB에 유지한다. 품목은 최대 1,000개다. 실제 Worker 무료 CPU 환경과 휴대전화 브라우저에 대한 새 기능 검증은 아직 수행하지 않았다.

## 배포 확인 — 2026-11-09 (한국 시간)

사용자가 공유한 Codespaces 최종 실행 화면에서 소스 `771622eb714d4a32683a05e2afd1cd4035eb23f3`의 `ONWORK_DEPLOY_OK`와 기존 주소 반영 및 공개 접속 검사 완료 메시지를 확인했다. 주소는 https://onwork-preview-20261007-01.hoon426865.workers.dev 로 유지된다.

실행 화면에는 무료 Workers/D1 구독 확인, 백업·복원 사본 검사, 이미 적용된 DB 변경 건너뛰기, 코드 배포와 공개 접속 검사의 완료가 표시됐다. 첫 실행에서 DB 가져오기 출력 해석이 실패했으나, 수정본은 DB를 다시 검사해 완료된 변경을 재적용하지 않고 배포를 마쳤다. 상세 DB 검사 결과와 Worker 버전은 사용자의 해당 실행 폴더 `release.json` 및 비공개 검사 자료에 보관된다.

확인 근거는 사용자가 공유한 최종 실행 화면이다. 이 작업 환경에서 원격 관리 API를 다시 조회한 결과는 아니다. 배포 후 실제 관리자·직원 로그인, 품목 JSON 가져오기, 담당자 권한 설정, 현장 업무와 무료 CPU 한도 검증은 아직 확인되지 않았다. 품목·검사기준 64개는 아래 5번의 관리자 가져오기로 적용한다.

## 배포 및 후속 설정 절차

최초 작업 환경의 Cloudflare 인증 결과 수신이 차단되어, 사용자가 선택한 기존 Codespaces에서 [배포 실행 안내](CODESPACES-OPERATIONS.md)의 도구로 배포했다. 향후 재실행에도 같은 보존·검사 절차를 사용한다.

1. 기존 Cloudflare 계정의 배포 인증을 복구한다. 비밀값을 채팅이나 Git에 넣지 않는다.
2. 기존 preview Worker/D1 대상과 계정, 현재 원격 버전/마이그레이션을 확인하고, 일관된 비공개 DB export 및 복구 검증을 준비한다. 기존 DB를 초기화/덮어쓰기/재이전하지 않는다.
3. 현재 스키마가 0006/0007/0008 중 어디까지 적용되었는지 사본에서 확인한다. 필요한 경우 `0007_test_data_reset.sql`과 `0008_operations.sql` 중 누락된 파일만 순서대로 적용하고 무결성/기존 자료 보존을 확인한다. 0007 적용은 자료 삭제를 실행하지 않는다. 과거 migration을 일괄 재실행하지 않는다.
4. 검증된 브랜치의 assets와 Worker를 기존 `--env preview` 대상에 배포한다. production 설정은 별도 환경이므로 사용하지 않는다.
5. 기존 관리자 패스키로 로그인해 설정의 품목 목록 가져오기에 비공개 `onwork-reference-catalog.json`을 적용한다. 동일 도면번호는 건너뛰며 실패 후 재시도해도 기존 기준을 덮어쓰지 않는다. 관리자와 협의한 실제 담당자만 지정한다.
6. 실제 주소의 로그인/메뉴/권한과 무료 실행 한도를 확인한다. 초기 재고는 확인된 실제 입고·재고 조정으로 등록한다. 테스트 자료를 운영 재고로 사용하지 않는다.

새 주소나 별도 운영 앱은 만들지 않았다. 후속 현장 확인 결과는 실제 확인 후 이 문서에 추가한다.
